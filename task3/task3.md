## 1. Технический радар

### 1.1. Текущее состояние (Hold — отказ от легаси)

| Технология | Назначение | Почему уходим | Бизнес-сценарий |
|------------|-----------|---------------|-----------------|
| **SQL Server 2008** | Монолитный DWH | Закончился lifecycle, не масштабируется, блокирует развитие | Все сценарии страдают, т.к. DWH — единая точка изменений |
| **PowerBuilder** | Интерфейс операторов клиник | Устаревшая платформа, нет API, сложно интегрировать с ИИ | Работа операторов: запись пациентов, просмотр карт |
| **Apache Camel (ESB)** | Интеграционная шина | Нет буферизации, точка-точка, сбои ведут к потере событий | Интеграция между сервисами (старый ландшафт) |
| **Power BI (кастомизации)** | BI-отчётность | Кастомизации жёстко привязаны к DWH, нет самообслуживания | Управленческая отчётность, KPI |

### 1.2. Оценка (Assess — изучаем)

| Технология | Назначение | Почему изучаем | Бизнес-сценарий |
|------------|-----------|----------------|-----------------|
| **dbt (data build tool)** | Трансформации данных в витрине | Декларативный подход к трансформациям, CI/CD, документация | Построение слоёв витрины данных, версионирование трансформаций |
| **Great Expectations** | Качество данных | Профилирование, проверки, мониторинг качества | Гарантия корректности данных в витрине для принятия решений |
| **Apache Iceberg / Delta Lake** | Формат таблиц для озера данных | ACID-транзакции, time-travel, schema evolution | Хранение исторических данных после вывода DWH |

### 1.3. Пилот (Trial — пилотируем)

| Технология | Назначение | Ожидаемый эффект | Бизнес-сценарий |
|------------|-----------|-----------------|-----------------|
| **Data Mesh** | Доменная архитектура данных | Команды владеют своими данными, независимый lifecycle | Интеграция новых бизнесов без изменения DWH |
| **DataHub / Amundsen** | Каталог данных | Поиск датасетов, линидж, управление доступом | Самообслуживание: аналитики находят нужные данные |
| **CockroachDB** | Геораспределённая БД для финтеха | Отказоустойчивость, compliance, низкая задержка | Финансовые сервисы: работа 24/7, геораспределение |
| **Apache Superset** | Портал самообслуживания | Конструктор дашбордов, SQL-лаборатория | Бизнес-пользователи строят отчёты без ИТ |
| **S3 / MinIO** | Объектное хранилище для ML-артефактов | Масштабируемое хранение моделей, датасетов | Хранение ML-моделей, обучение на исторических данных |

### 1.4. Внедрение (Adopt — внедряем)

| Технология | Назначение | Решаемая проблема | Бизнес-сценарий |
|------------|-----------|------------------|-----------------|
| **Kubernetes (K8s)** | Оркестрация контейнеров | Единая платформа для всех сервисов, автоскейлинг | Масштабирование отчётности, запуск новых сервисов |
| **Apache Kafka** | Событийная шина | Асинхронная интеграция доменов, буферизация, replay | Интеграция финтеха, ИИ, партнёров без DWH |
| **ClickHouse** | OLAP-витрина данных | Высокая производительность аналитических запросов (секунды вместо часов) | Сложные отчёты по финансам, загрузке клиник, KPI |
| **PostgreSQL** | Основная БД доменов | Надёжность, открытый код, расширяемость | Операционные данные клиник, HQ, партнёров |
| **Keycloak + OpenPolicyAgent** | IAM, RBAC, маскирование данных | Централизованное управление доступом, аудит | Безопасность медданных, финданных, compliance |
| **Debezium** | CDC из легаси | Миграция данных без остановки систем, минимальный downtime | Перенос исторических данных из SQL Server 2008 в Kafka |
| **Kong / Traefik (API Gateway)** | Единая точка входа для партнёров | Маршрутизация, rate limiting, JWT-валидация | Подключение фармы и производителей электроники |
| **MLflow** | Реестр ML-моделей | Версионирование, эксперименты, деплой | Управление моделями для диагностики, предиктивное обслуживание |
| **Terraform / Pulumi** | Infrastructure as Code | Управление инфраструктурой через код | Быстрое развёртывание сред для новых доменов / партнёров |
| **VictoriaMetrics / Prometheus + Grafana** | Мониторинг и алертинг | Наблюдаемость сервисов, SLA | Контроль качества медицинских и финансовых сервисов |

## 2. Роадмап изменений

### Этап 1. Фундамент и начало миграции (Месяцы 1–3)

**Бизнес-цель:** Остановить рост монолита, подготовить инфраструктуру для независимости доменов.

| Задача | Технологии | Ожидаемый результат | Ответственные | Ресурсы |
|--------|-----------|---------------------|---------------|---------|
| Развёртывание облачной инфраструктуры | K8s, Terraform, Azure/AWS | Рабочий кластер, CI/CD, IaC | Platform-команда (DevOps) | 2 DevOps, облачные квоты |
| Запуск событийной шины | Apache Kafka (Confluent / MSK) | Kafka-кластер, топики по доменам | Platform-команда + интеграция | 2 инженера, лицензия Confluent |
| CDC из легаси DWH | Debezium, Kafka Connect | Поток изменений из SQL Server 2008 → Kafka | Data-команда + DWH-команда | 2 инженера |
| Определение границ доменов | Data Mesh подход | Задокументированные границы, контракты событий | Архитектор + владельцы продуктов | Архитектор, product owners |
| Выбор и развёртывание IAM | Keycloak, OPA | Централизованная аутентификация, политики доступа | Security-команда | 1 Security Engineer |
| Развёртывание мониторинга | Prometheus, Grafana, VictoriaMetrics | Метрики сервисов, дашборды, алерты | Platform-команда | 1 DevOps |

**Бизнес-обоснование этапа:** За первые 3 месяца компания перестаёт зависеть от legacy DWH как единственного источника данных. Kafka становится новым интеграционным бэкбоном — любой новый сервис подключается через события, не трогая DWH. IAM сразу обеспечивает разграничение доступа к медицинским и финансовым данным.

### Этап 2. Доменная независимость (Месяцы 2–5)

**Бизнес-цель:** Каждый домен получает собственные БД и API, начинает публиковать события.

| Задача | Технологии | Ожидаемый результат | Ответственные | Ресурсы |
|--------|-----------|---------------------|---------------|---------|
| Выделение БД клинического домена | PostgreSQL | Отдельная БД клиник, миграция схемы | Клиническая команда | 2 бэкенд-разработчика |
| Выделение БД финтех-домена | CockroachDB | Геораспределённая БД для финтеха | Финтех-команда | 2 Go-разработчика |
| Развёртывание MLflow | MLflow, S3 / MinIO | Реестр моделей, версионирование | ИИ-команда | 1 ML-инженер, 1 Python-разработчик |
| Первые API доменов | Spring Boot (клиники), Go (финтех), FastAPI (ИИ) | Рабочие API для операционных данных | Соответствующие команды | По 1–2 разработчика на домен |
| Первые доменные события в Kafka | Kafka Producer (каждый домен) | События: AppointmentCreated, TransactionCompleted | Все команды | Интеграция с платформой |
| Создание домена партнёров | PostgreSQL, API Gateway (Kong) | Заглушка для будущих партнёров | Интеграционная команда | 1 разработчик |

**Бизнес-обоснование этапа:** Домены начинают работать независимо. Финтех запускает новые кредитные продукты без согласования с DWH. ИИ-команда получает собственную инфраструктуру для моделей. Клиники развязываются с монолитом. Параллельно (месяцы 2–3 и 2–5 идут внахлёст с этапом 1).

### Этап 3. Самообслуживание и витрина данных (Месяцы 4–8)

**Бизнес-цель:** Бизнес-пользователи получают возможность строить отчёты самостоятельно.

| Задача | Технологии | Ожидаемый результат | Ответственные | Ресурсы |
|--------|-----------|---------------------|---------------|---------|
| Развёртывание OLAP-витрины | ClickHouse | Кластер ClickHouse, потребление событий из Kafka | Data-команда | 2 Data-инженера |
| Запуск портала самообслуживания | Apache Superset | Портал с дашбордами, SQL-лаборатория | Data-команда + Frontend | 1 Frontend, 1 Data Analyst |
| Каталог данных | DataHub | Поиск датасетов, линидж, глоссарий | Data-команда | 1 Data Engineer |
| Интеграция потоков в витрину | Kafka → ClickHouse | AppointmentMeta, TransactionSummary, InventoryStats | Data-команда | 1 Data Engineer |
| Обучение бизнес-пользователей | — | Проведённые тренинги, первые отчёты | Data-команда + Product | Аналитики бизнеса |
| Настройка RBAC в портале | Keycloak + OPA | Роли: врач, аналитик, менеджер, аудитор | Security-команда | 1 Security Engineer |

**Бизнес-обоснование этапа:** Это этап, который непосредственно приносит ценность бизнесу. Отчёты вместо часов строятся за секунды. Бизнес-пользователи перестают ждать ИТ-специалистов. Каталог данных решает проблему «где лежат данные». Важно: медицинские карты и результаты исследований не попадают в витрину (ограничение настроено на уровне Kafka Consumer + OPA).

### Этап 4. Партнёры и масштабирование (Месяцы 7–12)

**Бизнес-цель:** Подключение фармацевтических компаний и производителя электроники, вывод легаси.

| Задача | Технологии | Ожидаемый результат | Ответственные | Ресурсы |
|--------|-----------|---------------------|---------------|---------|
| Включение API Gateway для внешних партнёров | Kong / Traefik | Rate limiting, JWT, документация OpenAPI | Platform-команда | 1 Platform Engineer |
| Интеграция фарм-компаний | Kafka, REST + Partner Domain | DrugCatalog update в реальном времени | Интеграционная команда | 2 разработчика, юрист |
| Интеграция производителя электроники | Kafka, MQTT over WebSocket | Equipment telemetry → Inventory + AI | Интеграционная команда | 2 разработчика |
| Доработка витрины для партнёрских данных | ClickHouse, Superset | Дашборды поставок, закупок, телеметрии | Data-команда | 1 Data Engineer |
| Вывод легаси DWH (частичный) | — | Отключение SQL Server 2008 для части доменов | Data-команда + DWH-команда | 1 Data Engineer, 1 DBA |
| Пост-миграционный аудит | OPA, Audit log | Проверка, что медданные не утекли в витрину | Security-команда | Аудит |
| План дальнейшей миграции PowerBuilder | — | Формирование ТЗ на новый интерфейс | Клиническая команда + Product | Product Manager |

**Бизнес-обоснование этапа:** Новые бизнес-направления (фарма, электроника) интегрируются без единого изменения в DWH — только через API Gateway и Kafka. Это ключевое преимущество целевой архитектуры. Производитель электроники не только поставляет данные для инвентаризации, но и подключает ИИ-модели для предиктивного обслуживания. К концу года компания может частично отключить SQL Server 2008.

## 3. Обоснование изменений (стратегическая карта)

### 3.1. Как изменения влияют на бизнес-метрики

| Бизнес-метрика | Текущее состояние | Целевое состояние | За счёт чего достигается |
|---------------|------------------|-------------------|------------------------|
| **Time-to-Market** нового продукта | 3–6 месяцев | 2–4 недели | Доменная архитектура: изменения в границах одного домена |
| **Скорость построения сложного отчёта** | Часы | Секунды | ClickHouse вместо SQL Server + Kafka-потоки |
| **Скорость подключения нового партнёра** | 2–3 месяца | 2–4 недели | API Gateway + событийная шина, без изменения DWH |
| **Затраты на поддержку инфраструктуры** | Высокие (оборудование, лицензии SQL Server) | Снижение на 30–40% | Облако (pay-as-you-go), отказ от SQL Server лицензий |
| **Доступность критичных сервисов** | 95–98% (single DC) | 99.9%+ (геораспределение) | K8s, CockroachDB, geo-redundancy |
| **Риск утечки медданных** | Высокий (всё в одном DWH) | Низкий (изоляция доменов) | Domain boundaries + IAM + OPA-политики |
| **Производительность разработки (команды)** | Блокировки, ожидание DWH-изменений | Параллельная разработка | Data Mesh: каждая команда владеет своим доменом |

### 3.2. Почему каждый этап критичен

**Этап 1 (Фундамент):**
- Без Kafka и CDC мы не можем начать развязывать домены — легаси остаётся единственным источником правды
- Без IAM мы не можем гарантировать, что медданные не утекут в витрину
- Без K8s мы не можем масштабировать сервисы под нагрузку отчётности

**Этап 2 (Домены):**
- Без собственных БД домены остаются привязаны к DWH — изменения требуют месяцев
- Без собственных API финтех не может запускать продукты независимо
- MLflow критичен для воспроизводимости и версионирования диагностических моделей (регуляторика)

**Этап 3 (Витрина):**
- Основная бизнес-ценность: скорость принятия решений и самообслуживание
- Без каталога данных аналитики тратят время на поиск «где лежат данные»
- Обучение пользователей — ключевой фактор adoption; без него портал не окупится

**Этап 4 (Партнёры):**
- Подключение фармы и электроники — прямой рост выручки через новые бизнес-направления
- Вывод легаси DWH сокращает операционные затраты (лицензии, поддержка, электричество)
- Пост-миграционный аудит гарантирует регуляторный compliance перед отключением старой системы

### 3.3. Риски и их митигация

| Риск | Митигация |
|------|-----------|
| **Потеря данных при миграции** | CDC (Debezium) + Kafka replay гарантируют доставку; параллельная работа legacy до полной верификации |
| **Сопротивление команд переходу на новые инструменты** | Обучение на этапе 3, вовлечение product owners в определение границ доменов на этапе 1 |
| **Задержки интеграции фармы из-за юридических вопросов** | Parallel workstream: юридическая проверка идёт одновременно с технической подготовкой (этап 4) |
| **Снижение производительности ClickHouse при пиковых нагрузках** | Автоскейлинг K8s + шардирование ClickHouse (закладывается на этапе 3) |
| **Утечка медданных через витрину** | На уровне Kafka Consumer настроен фильтр (не попадают события с медкартами); OPA-политики на уровне витрины; регулярный аудит |
