# Задание 2. Декомпозиция системы на домены

## 1. Выделенные домены

| Домен | Владелец | Описание | Границы ответственности |
|-------|----------|----------|------------------------|
| **Клинический домен** (Clinical) | Клиники | Операционная деятельность клиник: запись пациентов, управление персоналом, инвентаризация, медицинские карты, истории болезней, результаты исследований | Не публикует медицинские карты и результаты исследований в витрину данных. Предоставляет только обезличенные метрики (кол-во обращений, загрузка оборудования). |
| **Финтех-домен** (Fintech) | Финтех-компания (с банковской лицензией) | Банковские счета, транзакции, кредиты, финансовая история, платёжные сервисы | Полная независимость от DWH. Соблюдение 152-ФЗ, банковской тайны. |
| **ИИ-домен** (AI) | ИИ-компания | Обучение и инференс ML-моделей для анализа медицинских данных, диагностические рекомендации | Получает медицинские данные от клинического домена через защищённый канал. Публикует только мета-информацию результатов (без сырых данных). |
| **Корпоративный домен** (HQ) | Головной офис | Управленческая отчётность, консолидированные KPI, бюджетирование, OKR, HR-аналитика | Потребляет агрегированные данные из всех доменов. |
| **Партнёрский домен** (Partners) | Головной офис / Интеграционная команда | Интеграция фармацевтических компаний (справочники лекарств, поставки) и производителей электроники (телеметрия оборудования) | Единая точка входа для внешних партнёров. Маршрутизация данных в соответствующие домены. |
| **Платформа данных** (Data Platform) | Централизованная платформенная команда | Портал самообслуживания (витрина данных), каталог данных, IAM, аудит | Не содержит медицинских карт, историй болезней и результатов исследований. Только агрегированные, обезличенные метрики. |

## 2. Обоснование декомпозиции

### 2.1. Бизнес-сценарии и их обеспечение доменами

#### Сценарий А: Запуск нового кредитного продукта в финтехе

- **Текущая проблема**: Изменение в финтехе требует изменений в монолитном DWH.
- **В новой архитектуре**: Финтех-домен независимо разрабатывает API, БД и события. Публикует в Kafka события `LoanIssued`, `TransactionCompleted` и др. Витрина данных потребляет эти события для построения отчётности. DWH не трогается.

#### Сценарий Б: Использование ИИ для анализа диагностических данных

- **Поток**: Клинический домен → ИИ-домен (медицинские данные через защищённый канал) → ИИ-домен публикует мета-информацию (`DiagnosisMeta`) в Kafka → Витрина данных.
- **Ключевое решение**: ИИ-домен получает доступ к медицинским данным для инференса, но не имеет права пересылать сырые данные в другие системы. В витрину попадает только мета-информация (какой модели был сделан запрос, время обработки, уверенность предсказания — без самих медицинских данных).

#### Сценарий В: Подключение фармацевтической компании

- **Поток**: Фарм-партнёр → API Gateway → Партнёрский домен → Kafka → Клинический домен (справочник лекарств) и Финтех-домен (кредитование поставок).
- **Преимущество**: Партнёр подключается один раз к API Gateway, маршрутизация данных в нужные домены происходит через Kafka без изменения DWH.

#### Сценарий Г: Интеграция производителя электроники

- **Поток**: Производитель → API Gateway → Kafka → Клинический домен (инвентаризация) + ИИ-домен (предиктивное обслуживание).
- **Преимущество**: Телеметрия оборудования поступает напрямую в домены, минуя DWH.

#### Сценарий Д: Построение отчёта по загрузке оборудования по клиникам

- **Поток**: Клинический домен публикует события `InventoryChanged`, `EquipmentUsed` в Kafka → Витрина данных агрегирует → Бизнес-пользователь строит отчёт в портале самообслуживания.
- **Ограничение**: В витрине нет медицинских карт — только факт использования оборудования.

### 2.2. Логика разделения

| Критерий | Решение |
|----------|---------|
| **Независимость разработки** | Каждый домен имеет собственную БД, API и команду. Изменения в одном домене не требуют согласования с другими (только контракты событий в Kafka). |
| **Регуляторные требования** | Медицинские данные (врачебная тайна) и финансовые данные (банковская тайна) изолированы в соответствующих доменах. Витрина данных не содержит защищённых категорий данных. |
| **Масштабирование** | Каждый домен может масштабироваться независимо (например, финтех — CockroachDB для геораспределённости, клиники — PostgreSQL). |
| **Time-to-Market** | Новая функциональность реализуется в границах одного домена. Не требуется вносить бизнес-логику в DWH. |
| **Отказоустойчивость** | Сбой финтех-домена не влияет на клинический домен. Событийная шина гарантирует доставку сообщений. |

## 3. Потоки данных между доменами

### 3.1. Основные потоки

| Откуда | Куда | Данные | Канал | Триггер / Сценарий |
|--------|------|--------|-------|--------------------|
| Клиники | Kafka | `AppointmentCreated`, `InventoryChanged`, `EquipmentUsed`, `StaffSchedule` | Kafka Producer | Операционные события клиник |
| Финтех | Kafka | `TransactionCompleted`, `LoanIssued`, `AccountChanged` | Kafka Producer | Финансовые операции |
| ИИ-сервисы | Kafka | `DiagnosisMeta` (только мета), `ModelPrediction`, `ModelPerformance` | Kafka Producer | Результаты инференса |
| Головной офис | Kafka | `KPICalculated`, `BudgetPeriodClosed` | Kafka Producer | Периодическая отчётность |
| Фарм-партнёр | Клиники | DrugCatalog update | Kafka (через API Gateway) | Обновление справочника |
| Фарм-партнёр | Финтех | SupplierInvoice, DeliveryConfirmed | Kafka (через API Gateway) | Кредитование поставок |
| Производитель | Клиники | EquipmentTelemetry | Kafka (через API Gateway) | Инвентаризация |
| Производитель | ИИ | CalibrationData | Kafka (через API Gateway) | Предиктивное обслуживание |
| Клиники | ИИ | MedicalData (диагностические данные) | Защищённый gRPC/HTTP (внутренний) | Инференс ИИ-моделей |
| ИИ | Клиники | AIRecommendation | Защищённый gRPC/HTTP (внутренний) | Результаты диагностики |
| Kafka | Витрина данных | `AppointmentMeta`, `TransactionSummary`, `InventoryStats`, `ModelMeta` | Kafka Consumer | Построение витрины |
| Витрина данных | Портал | Агрегированные данные | SQL / REST | Самообслуживание |

### 3.2. Принципы организации потоков

- **Событийная шина (Kafka)** — единственный интеграционный backbone для асинхронных потоков. Заменяет старую ESB на Apache Camel.
- **Синхронные вызовы** — только для прямого обмена данными между Клиниками и ИИ (медицинские данные не покидают защищённый периметр).
- **CDC из легаси** — Debezium читает изменения из старого DWH (SQL Server 2008) и публикует в Kafka до полного вывода легаси из эксплуатации.
- **Витрина данных** — потребляет только обезличенные события. Никакие медицинские карты, истории болезней и результаты исследований не попадают в витрину.

## 4. Преимущества для бизнеса

| Преимущество | Описание |
|-------------|----------|
| **Ускорение Time-to-Market** | Новый продукт (например, кредитная карта) запускается в рамках одного домена за 2-4 недели вместо 3-6 месяцев при монолитном DWH. |
| **Снижение зависимости от DWH** | DWH (SQL Server 2008) выводится из эксплуатации. Легаси-системы не требуют изменений для новых бизнес-направлений. |
| **Независимость развития направлений** | Финтех, клиники и ИИ развиваются независимыми командами с разными технологическими стеками. |
| **Регуляторная безопасность** | Изоляция медицинских и финансовых данных. Соблюдение 152-ФЗ, ФЗ «Об основах охраны здоровья», банковской тайны. |
| **Масштабируемость** | Каждый домен использует оптимальную БД (PostgreSQL, CockroachDB, S3). Нагрузка не конкурирует за общий DWH. |
| **Упрощение интеграции партнёров** | Единый API Gateway и событийная шина. Новый партнёр подключается один раз, данные маршрутизируются автоматически. |
| **Производительность аналитики** | Витрина данных (ClickHouse/Snowflake) оптимизирована для OLAP-запросов. Отчёты строятся за секунды вместо часов. |
