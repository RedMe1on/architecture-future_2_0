# Обоснование конфигурации Terraform

## 1. Выбор ресурсов и параметров

### 1.1. Сеть (VPC, Subnets, NAT)

| Компонент | Выбор | Обоснование |
|-----------|-------|-------------|
| **VPC CIDR /16** | `10.0.0.0/16` | Достаточно для 65536 адресов — покрывает все текущие и будущие сервисы. Оставляем запас для новых доменов (фарма, электроника). |
| **Публичные подсети /24** | 3 шт. (по числу AZ) | Только для Bastion, NAT Gateway и Load Balancer. Минимизируем поверхность атаки: всё остальное — в приватных подсетях. |
| **Приватные подсети /24** | 9 шт. (по сервису) | Каждый сервис в изолированной подсети — упрощает Security Groups, аудит трафика, исключает случайное взаимодействие. |
| **NAT Gateway** | 1 шт. в public subnet | Обеспечивает outbound-доступ для приватных ВМ (обновления, загрузка образов). Выбран 1 NAT (cost-efficient); для production уровня можно сделать 3 (по AZ). |
| **Internet Gateway** | 1 шт. | Обеспечивает inbound-доступ к публичным ресурсам (Bastion, ALB). |
| **Security Groups** | Per-service | Минимальный принцип: разрешены только необходимые порты между конкретными подсетями. Kafka (9092) — только от K8s workers и API Gateway. ClickHouse (8123) — только от Superset. |

### 1.2. Вычислительные ресурсы (VM)

| Группа | Размер | vCPU | RAM | Диск | Обоснование |
|--------|--------|------|-----|------|-------------|
| **K8s Control Plane** | 3 × `4 vCPU / 16 GB` | 12 | 48 GB | 3 × 100 GB SSD | 3 узла для HA etcd. 4 vCPU — минимально для etcd+kube-apiserver+scheduler. 100 GB — для etcd-данных. |
| **K8s Workers** | 3 × `8 vCPU / 32 GB` | 24 | 96 GB | 3 × 200 GB SSD | Тяжёлые нагрузки: API-сервисы доменов, Superset, DataHub, Keycloak, Debezium. 8 vCPU — для параллельной обработки событий. 200 GB — образы контейнеров, логи. |
| **Kafka** | 3 × `4 vCPU / 16 GB` | 12 | 48 GB | 3 × 200 GB SSD | 3 брокера для отказоустойчивости (min.insync.replicas=2). 4 vCPU — на каждый брокер для пиковой пропускной способности. SSD обязателен для низкой задержки. |
| **ClickHouse** | 3 × `8 vCPU / 32 GB` | 24 | 96 GB | 3 × 500 GB SSD | 3 шарда для параллельной обработки запросов. 8 vCPU — для быстрых агрегаций. 500 GB SSD — большой объём аналитических данных. ClickHouse чувствителен к скорости диска. |
| **PostgreSQL** | 1 Primary + 1 Replica `4 vCPU / 16 GB` | 8 | 32 GB | 2 × 200 GB SSD | Primary + синхронная реплика для HA. 4 vCPU достаточно для операционных нагрузок доменов. 200 GB — данные клиник, HQ, партнёров. |
| **CockroachDB** | 3 × `4 vCPU / 16 GB` | 12 | 48 GB | 3 × 100 GB SSD | 3 узла для геораспределённой отказоустойчивости (Raft consensus). 100 GB — финансовые данные (счета, транзакции) умеренного объёма по сравнению с аналитикой. |
| **MinIO (S3)** | 3 × `4 vCPU / 16 GB` | 12 | 48 GB | 3 × 500 GB HDD | 3 узла для erasure coding. HDD — данные холодного хранения (ML-артефакты, бэкапы, логи). Скорость не критична. 500 GB — для моделей, датасетов, бэкапов. |
| **API Gateway** | 2 × `4 vCPU / 8 GB` | 8 | 16 GB | 2 × 50 GB SSD | 2 узла для HA. Kong/Traefik легковесны: 4 vCPU хватит для rate limiting, JWT, маршрутизации. 50 GB SSD — логи, конфиги. |
| **Bastion** | 1 × `2 vCPU / 8 GB` | 2 | 8 GB | 1 × 50 GB SSD | Только для SSH-доступа администраторов. Малый размер. |
| **Monitoring** | 1 × `4 vCPU / 16 GB` | 4 | 16 GB | 1 × 200 GB SSD | Prometheus + Grafana + VictoriaMetrics. 200 GB — метрики всех сервисов, retention 30 дней. |

## 2. Почему Infrastructure as Code (IaC) через Terraform

### 2.1. Декларативный подход

Terraform использует **декларативную модель**: мы описываем целевое состояние инфраструктуры, а не последовательность команд для его достижения. Это даёт:

- **Идемпотентность**: повторный `apply` не создаёт дубликатов, а приводит систему к целевому состоянию
- **План изменений**: `terraform plan` показывает точный diff до применения — инженер видит, какие ресурсы будут созданы/изменены/удалены
- **Автоматическое управление зависимостями**: граф ресурсов строится автоматически; PostgreSQL Replica создаётся после Primary

### 2.2. Воспроизводимость

- **Одна конфигурация — любой облачный провайдер**: меняем `provider` — получаем ту же архитектуру в AWS, Azure, GCP или Yandex.Cloud
- **Инфраструктура как код в Git**: полная история изменений, code review, rollback через `git revert`
- **Окружения (dev/staging/prod)**: один модуль с разными `tfvars` → идентичные среды

### 2.3. Масштабируемость

- **Параметризация через переменные**: меняем `instance_count["clickhouse"]` с 3 до 6 — Terraform добавит 3 узла с консистентной конфигурацией
- **Модульная архитектура**: каждый сервис — отдельный модуль; переиспользуем для новых доменов
- **Automated provisioning**: CI/CD (GitLab CI / GitHub Actions) запускает `terraform apply` при мерже в main

## 3. Terraform vs Manual: границы ответственности

| Компонент | Terraform | Ручная установка | Почему |
|-----------|-----------|------------------|--------|
| **VPC, Subnets, NAT, IGW** | ✅ | — | Базовая сетевая инфраструктура — стандартный IaC-сценарий |
| **Все VM и диски** | ✅ | — | Количество, размер, тип — переменные; изменения через PR |
| **Security Groups** | ✅ | — | Правила доступа — часть кода, обязательный code review |
| **K8s cluster setup** | 🔶 (kubeadm или managed K8s через провайдер) | ❌ (в схеме с null_resource — симуляция) | Managed K8s (EKS/AKS/GKE) можно через Terraform; bare-metal K8s — через Ansible |
| **Helm-чарты приложений** | — | ✅ | Конфигурация приложений часто меняется; Helm — отраслевой стандарт |
| **Kafka topics / Debezium** | — | ✅ | Настройка коннекторов — операционная задача, меняется часто |
| **Database schema migration** | — | ✅ | Выполняется CI/CD при деплое приложений |
| **DNS / SSL-сертификаты** | ✅ | — | Certificate Manager / Route53 — часть IaC |

## 4. Бизнес-обоснование выбранных параметров

### Почему ClickHouse на 8 vCPU / 500 GB SSD?
Основная жалоба бизнеса — отчёты строятся часами. ClickHouse — колоночная СУБД для OLAP-запросов. 8 vCPU на 3 узла = 24 ядра для параллельной обработки запросов. 500 GB SSD — аналитические данные за несколько лет. SSD критичен: ClickHouse использует подкачку на диск при нехватке RAM.

### Почему 3 брокера Kafka?
По стандарту Kafka: `min.insync.replicas=2` при `replication.factor=3` даёт отказоустойчивость при потере одного брокера. 3 брокера — минимальная конфигурация для HA (High Availability).

### Почему CockroachDB для финтеха?
Финансовые данные требуют геораспределённой отказоустойчивости (банковская лицензия). CockroachDB реализует Raft-консенсус и автоматическое восстановление при потере узла. 3 узла — минимальный кластер.

### Почему NAT Gateway (не NAT Instance)?
NAT Gateway — managed сервис облачного провайдера, не требует обслуживания. NAT Instance — отдельная ВМ, которую нужно настраивать и мониторить. Разница в цене оправдана надёжностью. Для dev-среды можно заменить на NAT Instance.

### Почему Security Groups per-service?
Минимизация поверхности атаки. Например, ClickHouse (8123) открыт только для K8s workers, где запущен Superset. Даже если ClickHouse будет скомпрометирован, злоумышленник не получит доступ к Kafka или PostgreSQL.
